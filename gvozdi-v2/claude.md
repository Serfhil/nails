# claude.md — правила проекта и маршрутизация агентов

Единственное место, где живут общие правила. Остальные документы ссылаются сюда и не повторяют их.
Все пути ниже — относительно `gvozdi-v2/` (корня проекта), если не сказано иное.

---

## 0. Первое действие любого агента: определить роль

Роль определяется **по первому сообщению** владельца или по явной передаче («Ты — роль Интерфейс»). До выбора роли агент не читает код, не правит файлы и не запускает субагентов.

| Если в сообщении… | Роль |
|---|---|
| ядро, движок, правила расчёта, `engine/`, `core.md`, баг в расчёте, сохранение, детерминизм, мини-фикстура | **Ядро** |
| пак, контент, баланс, тексты игры, товары, события, заказы, концовки, `packs/`, «добавь действие/персонажа/событие» | **Контент** |
| интерфейс, экран, кнопка, панель, вёрстка, цвета, телефон, `ui/`, сборка вида | **Интерфейс** |
| валидатор, проверка пака, коды `Vxxx`/`Wxxx`, сломанный пак, `validator/` | **Валидатор** |
| симулятор, прогоны, метрики открытого контента, `sim` (только по прямой просьбе) | **Симулятор** |
| запусти/собери игру, `dist/`, интеграция, несколько ролей сразу, `CONTRACT_ISSUES.md`, «сделай по ТЗ из claude.md», правка самих документов | **Оркестратор** |

**Правила выбора:**
1. Роль однозначна — первой строкой ответа назвать её и перечислить, что будет прочитано: «Роль: Интерфейс. Читаю claude.md §0–§4, view.md».
2. Неоднозначно (подходят две роли и больше, либо задача общая — «исправь баг», «улучши игру», «кнопка не работает», когда непонятно, вид это или расчёт) — **до всякого чтения и правок задать владельцу один вопрос** с вариантами ролей (инструмент выбора) и ждать ответа. Не угадывать.
3. Задача на несколько ролей сразу — это работа Оркестратора: он разбивает её на роли (§8).
4. Роль не меняется в ходе сессии. Нужна работа другой роли — это эскалация (§5), а не переключение.

**Сразу после выбора роли — `TASKS.md`.** Агент читает `TASKS.md` (§9) и выбирает открытые задачи с меткой своей роли (Оркестратор — ещё и с меткой `?` и с несколькими ролями). В первом ответе одной строкой перечисляет их номера: «Задачи для роли: T-003, T-007» или «Задач для роли нет». В работу берёт, только если владелец попросил (в первом сообщении или в ответ). Чужие задачи не выполняет.

**Просьба только записать задачу** («запиши в задачи …») роли не требует: любой агент дописывает запись в `TASKS.md` по §4 п. 2, коротко подтверждает номер и больше ничего не делает.

## 1. Проект

Движок текстового инкрементала про мастерскую и первый пак к нему — «Гвозди для графа»: деревенский кузнец растёт от гвоздей руками до хозяина мастерской, учит подмастерьев, берёт заказы знати. Время идёт только от действий игрока. Забег — 35–40 минут. Реиграбельность — через скрытый контент: его больше, чем видно за один забег. Играется на телефоне. Тексты игры — по-русски.

Три слоя, строго раздельно:
- **движок** знает общие механизмы и ничего о конкретной игре;
- **пак** описывает всю конкретику данными (JSON);
- **интерфейс** показывает вид движка и отправляет команды, ничего не считает.

В коде движка, валидатора, симулятора и интерфейса нет ни одного `id`, названия или текста пака (кроме зарезервированных переменных core.md 4.3 и слов самого контракта). Пак не меняет движок. Интерфейс не меняет движок.

## 2. Карта ролей: кто что пишет и читает

**Пишет** — единственные места, где роль вправе создавать и менять файлы. Всё остальное для неё read-only или закрыто.
**Читает** — вводные роли. Чтение сверх списка — только точечно, через граф (§3).

| Роль | Спецификация (читает целиком) | Пишет только | Дополнительно читает | Отчёт |
|---|---|---|---|---|
| **Ядро** | `core.md` | `engine/`, `fixtures/mini-pack/`, `docs/engine/` | — | `reports/core.md` |
| **Контент** | `content.md` (в нём копия core §4) | `packs/nails_for_count/` | вывод `npm run validate`; `docs/validator/README.md` (коды ошибок); `fixtures/mini-pack/` как образец | `reports/content.md` |
| **Интерфейс** | `view.md` (в нём копия core §5) | `ui/`, `docs/ui/` | `fixtures/mini-pack/` как вход; публичный вход движка `engine/src/index.ts` (только импорт, код движка не читать); `core.md` §6 (отладочный вид) — по необходимости | `reports/view.md` |
| **Валидатор** | `validator.md` + `core.md` разд. 4 (формат пака) | `validator/`, `fixtures/broken/`, `docs/validator/` | `fixtures/mini-pack/` и `packs/*` как данные (read-only) | `reports/validator.md` |
| **Симулятор** | `simulator.md` + `core.md` разд. 5–6 (API, вид, отладочный вид) | `simulator/`, `docs/simulator/` | `fixtures/mini-pack/`, `packs/*` (данные, read-only); движок — в порядке simulator.md §2.1 (публичный вход, `docs/engine/`, `loadPack` валидатора) | `reports/simulator.md` |
| **Оркестратор** | этот файл | корень проекта (`package.json`, `tsconfig.json`, `scripts/`), корень репозитория `blacksmith/` (`.gitignore`, `.github/`, `README.md`), `dist/`, `reports/orchestrator.md`, `CONTRACT_ISSUES.md`, спецификации (§6), `graphify-out/` | отчёты ролей `reports/*.md` | `reports/orchestrator.md` |

Что **не** читает каждая роль, пока не попросили: чужие спецификации (`view.md` для Ядра, `content.md` для Интерфейса и т. д.), чужой код, `reports/` других ролей, `decisions-log.md`.

## 3. Как читать проект: сначала граф, потом файлы

Граф проекта — `graphify-out/` в `blacksmith/` (рядом с папкой проекта). Он нужен, чтобы **не перечитывать проект целиком**.

Порядок для любой роли:
1. Прочитать этот файл (§0–§5) и **свою** спецификацию из §2.
2. Для вопросов «где это лежит», «что с чем связано», «кто это вызывает» — не открывать файлы наугад: `/graphify query "<вопрос>"` (широко), `--dfs` (проследить цепочку), `/graphify explain "<понятие>"`, `/graphify path "<А>" "<Б>"`. Запускать из `blacksmith/`. Обзор сообществ — только верхняя часть `graphify-out/GRAPH_REPORT.md` (раздел Community Hubs), не весь отчёт.
3. Открывать только те файлы и диапазоны строк, которые назвал граф и которые лежат в зоне чтения роли.
4. Граф — навигатор, а не источник истины. Правила и формат берутся из текста спецификации, не из ответа графа. Граф устарел или молчит — открыть нужный файл напрямую, не пересобирать граф самому.

Запрещено: читать проект целиком; открывать `node_modules/`, `dist/`, `graphify-out/cache/`, `_archive/`; читать код движка Интерфейсу, Контенту и Валидатору «для понимания» (их ТЗ рассчитано на работу без него).
Пересборка графа (`/graphify . --update`) — только Оркестратор, после крупных правок и перед запуском ролей.

## 4. Правила работы в своей зоне

1. **Только своя зона.** Пишешь исключительно в папки из столбца «Пишет только». Мелкая правка «по дороге» в чужом файле — тоже нарушение. Исключения для всех ролей — дописывание `CONTRACT_ISSUES.md` и `TASKS.md` (§9).
2. **«Запиши в задачи …».** Любой агент по такой просьбе владельца дописывает запись в `TASKS.md`, даже если задача не для его роли, и не выполняет её, если она чужая. Метку роли ставит по таблице §0; неясно — `?`. Мысль владельца записывается близко к его словам, без додумывания.
3. **Спецификации не правит никто, кроме Оркестратора** (`claude.md`, `core.md`, `content.md`, `view.md`, `validator.md`, `simulator.md`, `decisions-log.md`) и только по решению владельца (порядок для новых правил — §8, «Новое правило от владельца»). Роль, нашедшая в своей спецификации ошибку, пишет запись в `CONTRACT_ISSUES.md`.
4. **core.md приоритетен над всеми документами.** Любое расхождение — запись в `CONTRACT_ISSUES.md`; работа идёт с самым простым вариантом, не нарушающим core.md.
5. **Дыра в контракте** — запись в `CONTRACT_ISSUES.md` (§9) и обходной простой вариант, а не домысел и не правка чужого.
6. **Контентмейкер не меняет движок**: использует его возможности; если задача не решается, пишет «не получится, потому что …» в `CONTRACT_ISSUES.md` и в отчёт и переходит к следующей.
7. **Интерфейс ничего не считает**: нужно поле, которого нет в виде, — запись в `CONTRACT_ISSUES.md`.
8. На каждый новый или переделанный модуль — md-описание в `docs/<зона>/` (назначение, поля, правила, примеры).
9. Стек: TypeScript, Node ≥ 20; интерфейс — обычный веб без тяжёлых фреймворков. Автоматические тесты баланса не делаются.
10. Репозиторий — `github.com/Serfhil/nails`, корень — `blacksmith/`. Коммиты и push делает только Оркестратор и только по просьбе владельца; роли не коммитят. `chat-context/` и `_archive/` не публикуются никогда (`.gitignore`). Каждый push в `main` публикует сайт на GitHub Pages.
11. Не уверен, чья это зона или роль, — спросить владельца (§0, п. 2), а не действовать.

## 5. Эскалация: что делать, когда нужна чужая зона

| Ситуация | Действие |
|---|---|
| Баг или нехватка в чужом коде/паке | Запись в `CONTRACT_ISSUES.md` с указанием роли-владельца + строка в своём отчёте. Чужое не править |
| Нужна правка спецификации | Запись в `CONTRACT_ISSUES.md`; решает Оркестратор, а при изменении core.md — владелец |
| Задача требует нескольких ролей | Остановиться, сообщить владельцу/Оркестратору; не расширять зону |
| Спецификации противоречат друг другу | Верен core.md; запись в `CONTRACT_ISSUES.md` |

## 6. Документы и их статус

| Документ | Для кого | Статус |
|---|---|---|
| `core.md` | Ядро; фрагменты — всем | **Приоритетный** контракт и ТЗ движка |
| `content.md` | Контент | Руководство; разд. 2 — копия core §4 |
| `view.md` | Интерфейс | Руководство; разд. 2 — копия core §5 |
| `validator.md` | Валидатор | ТЗ валидатора |
| `simulator.md` | Симулятор | ТЗ симулятора; **только по прямой просьбе владельца** |
| `claude.md` | все | Этот файл |
| `decisions-log.md` | справка | История решений; при расхождении верен core.md |
| `CONTRACT_ISSUES.md` | запись — все, разбор — Оркестратор | Журнал вопросов к контракту, найденных ролями |
| `TASKS.md` | запись — все, по просьбе владельца | Задачи и мысли владельца; каждая роль читает на старте (§0) |

**Копии контракта.** В `content.md` (между `<!-- sync:core-4:begin/end -->`) и `view.md` (`sync:core-5`) разделы core.md 4 и 5 не редактируются руками. После любой правки core.md Оркестратор запускает `npm run docs:sync`; `npm run docs:check` падает при расхождении.

**Устарело и не используется как ТЗ:** ТЗ ядра раунда 1 и файлы прежней версии игры (`GAME.md`, `CONTENT.md`, `DECISIONS.md`, `README.md`, прежний `CLAUDE.md`), всё в `_archive/`. Читать можно только как справку о духе и тоне игры.

## 7. Команды проекта

```
npm test                           # тесты движка, валидатора, интерфейса, симулятора
npm run test:engine | test:validator | test:ui | test:sim
npm run typecheck

```

## 8. Оркестратор

Основной агент. Сам код ролей не пишет: режиссирует.

**Обязанности:**
- определяет, какие роли нужны задаче, и запускает по одному субагенту на роль;
- держит порядок и зоны (§2), принимает отчёты, разбирает `CONTRACT_ISSUES.md`;
- разбирает `TASKS.md`: задачам с меткой `?` назначает роль (спросив владельца, если неясно), задачи на несколько ролей раскладывает по ролям; в задачу субагенту включает номера `T-NNN`, которые тот должен взять;
- собирает проект, подключает интерфейс к движку и паку, проверяет итог командами §7;
- правит спецификации по решению владельца и запускает `docs:sync`;
- обновляет граф после крупных правок.

**Новое правило от владельца** («у действий должны быть описания», «теперь так принято»). Просьба владельца в чате — и есть его решение. Порядок:
1. Определить, каких ролей правило касается (по таблице §0 и зонам §2). Ответ «какие роли затронуты» назвать владельцу одной строкой.
2. Записать правило в спецификацию **каждой** затронутой роли (`core.md`, `content.md`, `view.md`, `validator.md`, `simulator.md`) — там, где роль его прочтёт, в её терминах. В `claude.md` — только если правило общее для всех ролей. Формулировка близко к словам владельца, без додумывания; неясное — спросить до правки.
3. **`core.md` — сначала diff.** Показать владельцу предлагаемую правку и ждать «да»; только потом править и запускать `npm run docs:sync` (затем `docs:check`). Остальные спецификации правятся сразу.
4. **Последствия.** Контент и код, которые могли перестать соответствовать правилу, не переделывать и субагентов не запускать. Записать в `TASKS.md` по задаче на каждую затронутую роль (§9): что за правило, где оно записано, какие места могли измениться. Статус — «открыта».
5. Коротко отчитаться владельцу: какие файлы изменены, какие `T-NNN` созданы.

**Шаблон задачи субагенту** (всегда в таком виде, чтобы роль не нужно было угадывать):
```
Роль: <Ядро|Контент|Интерфейс|Валидатор|Симулятор>.
Прочитай claude.md §0–§5 и <спецификация роли>. Другие спецификации не читай.
Пиши только в: <папки зоны>. Остальное — read-only; нужна чужая правка — запись в CONTRACT_ISSUES.md.
Читай проект через граф (claude.md §3), не целиком.
Задача: <что сделать>.
Задачи из TASKS.md: <T-NNN, … или «нет»>; по завершении удали их из TASKS.md, итог — в отчёт (§9).
Сдача: проверки зоны + reports/<роль>.md.
```

**Порядок.** Ядро → (параллельно Валидатор и Интерфейс на `fixtures/mini-pack`) → Контент после зелёного валидатора → интеграция → итог. Симулятор — только по прямой просьбе владельца.

**Разбор `CONTRACT_ISSUES.md`.** Вопрос, решаемый без изменения core.md, Оркестратор решает сам и пишет решение в запись. Вопрос, требующий изменить core.md, не решает: собирает в итоговый отчёт владельцу. После решения владельца — правка core.md, `docs:sync`, уведомление затронутых ролей.

**Итоговая проверка:** `npm test`, `npm run typecheck`, `npm run docs:check`, `npm run validate -- packs/nails_for_count`, `npm run build`; поиск `id` пака в `engine/src` и `ui/src` — пусто.

## 9. Форматы

### Отчёт роли
`reports/<роль>.md`, кратко и сухо:
```
# <Роль>
Сделано: …
Не сделано и почему: …
Открытые вопросы: …
Как проверить: команды
```

### Запись в CONTRACT_ISSUES.md
Одна запись на вопрос, дописывается в конец, чужие записи не правятся (решение дописывает Оркестратор):
```
## CI-NNN <кратко>
Роль: …
Документ и раздел: …
Суть: …
Предлагаемый вариант: …
Что сделано пока: …
Решение оркестратора: … (или «требует изменения core.md — к владельцу»)
```

### Запись в TASKS.md
Одна запись на мысль владельца, дописывается в конец. Номер — следующий свободный `T-NNN`: больше самого большого номера, упомянутого в `TASKS.md` и в `reports/*.md` (номера не переиспользуются). Чужие записи не правятся, кроме строки «Статус» своей роли.
**В `TASKS.md` только открытые задачи, истории нет.** Выполненную или отклонённую задачу роль удаляет из файла целиком, а итог («T-NNN: что сделано, где» или «T-NNN отклонена: почему») пишет в свой отчёт `reports/<роль>.md`. Задачу на несколько ролей удаляет последняя, закончившая свою часть; до этого каждая дописывает в «Статус», что её часть готова.
```
## T-NNN <кратко>
Роль: <Ядро|Контент|Интерфейс|Валидатор|Симулятор|Оркестратор|?> (можно несколько через запятую)
Добавлено: <дата>, записал <роль агента>
Суть: <мысль владельца, близко к его словам>
Статус: открыта | в работе (<роль>, <дата>)
```
Отличие от `CONTRACT_ISSUES.md`: там — дыры и противоречия контракта, найденные ролями; здесь — задачи и идеи владельца.
